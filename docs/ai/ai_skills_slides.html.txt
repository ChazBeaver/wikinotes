      <section class="slide" data-title="Example A · release-notes" data-layer="model">
        <div class="eyebrow"><span class="sec">9 · Example A · auto-invoked workflow</span><span class="num"></span></div>
        <div class="body">
          <h2>A model-invoked workflow with a script, a reference file, and a template.</h2>
<pre class="code">---
<span class="k">name:</span> release-notes
<span class="k">description:</span> >
  <span class="h">Generates release notes from merged PRs between two git tags or refs.</span>
  <span class="s">Use when asked to "write release notes", "draft the changelog", "what shipped since vX",
  "summarize this release", or before cutting a release.</span> <span class="bad">Does not create tags or publish.</span>
---
<span class="c">## Procedure</span>
1. Determine the range. If the user gave two refs, use them. Otherwise run <span class="s">scripts/last-two-tags.sh</span>.
2. Collect merged PRs: <span class="s">scripts/prs-in-range.sh FROM TO</span> → one JSON object per line.
3. Group by label using the mapping in <span class="s">references/style.md</span>. Unlabeled → "Other".
4. Rewrite each title as a user-facing sentence. Tone and banned words: <span class="s">references/style.md</span>.
5. Write RELEASE_NOTES.md from <span class="s">assets/release-notes.md</span>.
6. Report counts per section and any PRs dropped as internal-only.
<span class="c">## Never</span>
- Never invent a PR not in the script output.  - Never create or push a tag.
<span class="c">## Done when</span>
RELEASE_NOTES.md exists, every PR is listed or reported dropped, and the user has the counts.</pre>
          <ul class="points">
            <li><b>Every step names a file or command.</b> Nothing is left for the model to guess.</li>
            <li><b>The deterministic parts are scripts.</b> Tag discovery and PR listing never vary.</li>
            <li><b>Done when</b> gives it a stop and a report format.</li>
          </ul>
        </div>
        <aside data-notes><h4>Notes · 3 min</h4><p>Full files including both scripts are in the manual, section 6. Here, point at three things: the quoted phrases, the file names in steps, and "Done when".</p></aside>
      </section>

      <section class="slide" data-title="Example B · ship" data-layer="disk">
        <div class="eyebrow"><span class="sec">10 · Example B · human-only, side effects</span><span class="num"></span></div>
        <div class="body">
          <h2>A skill that commits and pushes. Instructions guide behavior; host policy provides the security boundary.</h2>
<pre class="code">---
<span class="k">name:</span> ship
<span class="k">description:</span> >
  <span class="h">Stages, commits, and pushes the current branch</span> with a conventional commit message, then opens a PR.
  <span class="s">Invoke with /ship. Only when the user explicitly asks to ship, commit and push, or open a PR.</span>
<span class="k">disable-model-invocation:</span> true            <span class="c"># Claude Code honors this; Codex and OpenCode ignore it</span>
---
<span class="c">## Procedure</span>
1. <span class="s">git status --porcelain</span>. Empty? Stop: nothing to ship.
2. Refuse the default branch. Review the full diff and list untracked files; flag likely secrets.
3. Draft a subject and explicit path list. <span class="bad">Ask the user to approve exactly those paths and actions.</span>
4. Stage only approved paths; show <span class="s">git diff --cached</span>. Ask again if the staged diff changed.
5. Commit; push <span class="s">HEAD</span>; open the PR. Warn that Git hooks execute local code.
<span class="c">## Never</span>
- Never use git add -A.  - Never interpolate untrusted text into a shell command.  - Never force-push.</pre>
          <ul class="points">
            <li><b>The description still has triggers.</b> A person has to find it in a list.</li>
            <li><b>The confirmation is defense in depth.</b> Enforce write/network limits in the harness or sandbox.</li>
            <li><b>Review what is staged,</b> not only the working-tree summary. Git hooks can run on commit and push.</li>
          </ul>
        </div>
        <aside data-notes><h4>Notes · 3 min</h4><p>"This is the shape for anything with side effects: commit, deploy, send a message. Notice where the safety lives." Point at step 4.</p></aside>
      </section>

      <section class="slide" data-title="Example C · knowledge" data-layer="ctx">
        <div class="eyebrow"><span class="sec">11 · Example C · pure knowledge</span><span class="num"></span></div>
        <div class="body">
          <h2>Not every skill is a procedure. Some inject conventions when a topic comes up.</h2>
<pre class="code">---
<span class="k">name:</span> api-error-conventions
<span class="k">description:</span> >
  <span class="h">House conventions for HTTP error responses</span> in the public API. <span class="s">Use when writing or reviewing any
  handler that returns a 4xx or 5xx, adding a new error code, or touching files under api/errors/.
  Triggers: error response, status code, problem details, error code, validation error.</span>
<span class="k">user-invocable:</span> false                       <span class="c"># not a command; only the model brings it in</span>
---
All error responses use RFC 9457 Problem Details.
<span class="c">## Shape</span>   { "type": "https://api.example.com/errors/validation-failed", "title": "Validation failed",
             "status": 422, "detail": "...", "instance": "/users/123", "errors": [ ... ] }
<span class="c">## Rules</span>
- type is a stable URL. Add new ones to api/errors/registry.go and nowhere else.
- 422 for validation, 409 for state conflicts, 404 only when the path itself doesn't exist. Never 400 for validation.
- Never leak stack traces, SQL, or internal hostnames in detail.
- Every new error code needs a test in api/errors/registry_test.go.</pre>
          <ul class="points">
            <li><b>No steps, no scripts.</b> Rules plus one canonical example.</li>
            <li><b>Short.</b> It loads whenever error handling comes up, so it stays tight.</li>
            <li><b>Not in CLAUDE.md</b> because it's only relevant to some tasks.</li>
          </ul>
        </div>
        <aside data-notes><h4>Notes · 2 min</h4><p>"This is the answer to 'where do our conventions go?' Not CLAUDE.md, unless they apply to every task. A knowledge skill loads only when the topic shows up."</p></aside>
      </section>

            <table class="anti">
              <tr><th>Anti-pattern</th><th>Fix</th></tr>
              <tr><td>One giant skill for a whole domain</td><td>Split into narrow skills with sharp triggers</td></tr>
              <tr><td>Description explains the domain</td><td>List the phrases people type</td></tr>
              <tr><td>Tutorial content in the body</td><td>Keep only what's specific to your setup</td></tr>
              <tr><td>Overlapping descriptions</td><td>Distinct trigger set and exclusion each</td></tr>
              <tr><td>Reasoning through deterministic steps</td><td>Ship a script</td></tr>
              <tr><td>Relying on a Claude-only flag for safety</td><td>Put the confirmation step in the body</td></tr>
              <tr><td>Three copies in three directories</td><td>One canonical copy, symlinked</td></tr>
              <tr><td>Restating CLAUDE.md</td><td>Reference it; it's already loaded</td></tr>
            </table>
          </div>
          <ul class="points">
            <li><b>If the description needs "and" three times,</b> it's two skills.</li>
            <li><b>If two skills could both match a phrase,</b> the model will pick inconsistently.</li>
            <li><b>If work is deterministic,</b> consider a reviewed helper with validation, limits, and least privilege.</li>
          </ul>
